## 1. Контекст проблемы

В исходной реализации координации все события (`task_started`, `task_completed`, `research_*`) и снимки активных задач (`.current_task_<ALIAS>`) коммитятся и пушатся напрямую в ветку `main` репозитория `Common`:
```text
Common/
├── data/
│   └── progress/
│       ├── .current_task_EK
│       └── events/EK/2026.jsonl
```

### Недостатки коммитов в `main`
1. **Зашумление Git-истории (Commit Noise):** частые микро-события (старт исследования, смена статуса) генерируют десятки коммитов вида `chore(progress): EK task_started ...` в основной ветке, смешиваясь с реальными изменениями документации и кода.
2. **Риск случайных merge-конфликтов:** хотя файлы разделены по авторам (`.current_task_<ALIAS>`), частые `git pull --rebase` на `main` создают потенциальные коллизии в общих индексах.
3. **Психологический барьер у внешних команд:** инженеры не любят, когда автоматические служебные тулы непрерывно спамят коммитами в основную ветку репозитория.

## 2. Архитектурные альтернативы хранения статусов

Существует 4 проверенных способа хранить и синхронизировать статусы задач Координатора через Git, **не загрязняя ветку `main`**:

### Вариант 1: Изолированная ветка состояния (Orphan State Branch) — *Рекомендуемый*
* **Суть:** создать отдельную «сиротскую» ветку (без общего дерева файлов с кодом), например, `coordinator-state` или `meta/state`:
  ```bash
  git checkout --orphan coordinator-state
  git rm -rf .
  # В этой ветке живут только data/progress/ и события
  ```
* **Как работает:**
  * Репозиторий `Common` на ветке `main` содержит только документацию и чистую историю.
  * Скрипт `sync_event.sh` пушит обновления статусов исключительно в ветку `origin/coordinator-state` (через временный `git worktree` или фоновый push).
  * Разработчики работают на `main` и вообще не видят в своем `git log` служебных коммитов Координатора.

### Вариант 2: Кастомные Git-ссылки (Custom Git Refs / Namespaces)
* **Суть:** Git позволяет хранить любые ветки и ссылки за пределами стандартного пространства `refs/heads/*`.
* **Как работает:**
  * Снимки пушатся в специальное пространство ссылок:
    ```bash
    git push origin HEAD:refs/coordinator/slots/EK
    git fetch origin refs/coordinator/*:refs/remotes/origin/coordinator/*
    ```
  * Эти ссылки не отображаются в обычном списке веток (`git branch`), не требуют переключения веток на диске и не влияют на `main`.
  * Используется в Gerrit, GitHub PR (`refs/pull/*`) и сложных DevOps-пайплайнах.

### Вариант 3: Механизм Git Notes (`git notes`)
* **Суть:** штатный механизм Git для добавления метаданных к коммитам без изменения самих коммитов.
* **Как работает:**
  * Метаданные сессии и потраченные токены привязываются к коммитам веток задач через `git notes --ref=coordinator add ...`.
  * Синхронизируются отдельной командой `git push origin refs/notes/coordinator`.

### Вариант 4: Выделенный репозиторий координации (Dedicated Coordinator Repo)
* **Суть:** вынос `data/progress/` из репозитория `Common` в отдельный служебный репозиторий организации (например, `coordinator-bus` или `.coordinator-state`).
* **Плюсы:** идеальная изоляция — продуктовые репозитории и репозиторий документации остаются стерильно чистыми.

## 3. Облачный фронтенд и бэкенд прямо в GitHub (Backendless Git Architecture)

Возникает фундаментальный вопрос: **можно ли развернуть облачный Координатор (и фронт, и бэк) целиком внутри GitHub, вообще не арендуя сторонние VPS, базы данных и облачные сервисы?**

Ответ: **Да.** GitHub предоставляет готовую платформенную инфраструктуру, позволяющую полностью избавиться от выделенного бэкенд-сервера.

```text
               ┌────────────────────────────────────────────────────────┐
               │    ФРОНТЕНД (React SPA на Private GitHub Pages)        │
               │    - Доступ: https://<org>.github.io/coordinator/      │
               │    - Авторизация: GitHub PAT / OAuth текущего юзера    │
               └──────────────────────────┬─────────────────────────────┘
                                          │
                            прямые REST / GraphQL вызовы
                             (CORS поддерживается на 100%)
                                          │
               ┌──────────────────────────▼─────────────────────────────┐
               │              БЭКЕНД: САМ GITHUB API                    │
               │             (api.github.com / contents)                │
               │   - Чтение снимков задач (GET /contents/...)           │
               │   - Коммиты настроек из браузера (PUT /contents/...)   │
               │   - Контроль доступа: встроенный GitHub RBAC           │
               └──────────────────────────┬─────────────────────────────┘
                                          │
                                 событийный триггер
                              на git push в state-ветку
                                          │
               ┌──────────────────────────▼─────────────────────────────┐
               │          ФОНОВЫЙ ПРОЦЕССИНГ: GITHUB ACTIONS            │
               │   - Детекция коллизий сервисов и алерты в Slack        │
               │   - Блокировка мерджа в PR при нарушении гейтов        │
               │   - Агрегация аналитики FinOps (spend breakdown)       │
               └────────────────────────────────────────────────────────┘
```

### 3.1. Фронтенд на Private GitHub Pages
* React SPA компилируется в статические ассеты (`index.html`, `js`, `css`) и публикуется в **GitHub Pages** служебного репозитория организации.
* **Встроенный корпоративный доступ (Private Pages):** на тарифах GitHub Team/Enterprise доступ к Pages настраивается как приватный. Дашборд открывается только авторизованным сотрудникам организации. Не нужно писать собственную систему логина/паролей.

### 3.2. Бэкенд: GitHub API вместо собственного сервера
Фронтенд в браузере выполняет HTTP-запросы напрямую к `https://api.github.com`:
* **Поддержка CORS:** GitHub API официально отдает заголовок `Access-Control-Allow-Origin: *`, что позволяет браузерному клиенту работать без прокси.
* **Работа под правами текущего пользователя:** пользователь вводит свой Personal Access Token (или логинится через OAuth). Все запросы идут от его имени, наследуя реальные права доступа к репозиториям организации.
* **Rate Limits:** авторизованный токен получает 5 000 запросов в час. Запросы с заголовком `If-None-Match` (ETag) возвращают `304 Not Modified` и **вообще не расходуют квоту**.

## 4. Панель управления (Control Plane) прямо из браузера: коммиты без консоли

Фронтенд может не только читать состояние, но и **создавать реальные Git-коммиты прямо из браузера**. Это позволяет реализовать полноценное изменение настроек Координатора на GitHub Pages.

### 4.1. Механизм прямой записи через GitHub Contents API
Когда тимлид в веб-дашборде меняет переключатель (например, язык проекта или состав команды) и нажимает «Сохранить», браузер выполняет один `PUT`-запрос:

```typescript
// Прямой коммит изменений настроек из браузера в Git
const response = await fetch(
  'https://api.github.com/repos/Alina-Assist/Common/contents/data/settings/locale.json',
  {
    method: 'PUT',
    headers: {
      'Authorization': `Bearer ${userToken}`,
      'Content-Type': 'application/json',
      'Accept': 'application/vnd.github.v3+json',
    },
    body: JSON.stringify({
      message: 'chore(settings): update locale to ru via Coordinator Dashboard',
      content: btoa(JSON.stringify(updatedLocaleJson, null, 2)), // Base64
      sha: currentFileSha, // Optimistic Locking
      branch: 'main',
    }),
  }
);
```

### 4.2. Ключевые свойства браузерных коммитов

1. **Встроенный Optimistic Locking (Защита от затирания):**
   Поле `sha` содержит хэш предыдущей версии файла. Если два лида одновременно открыли настройки, и один нажал «Сохранить» раньше, второй запрос упадет с ошибкой `409 Conflict`. Случайно затереть чужие правки невозможно.
2. **Атомарность пакета файлов (GitHub GraphQL API):**
   Если требуется обновить сразу несколько файлов (например, `team.json` и `project_profile.json`), мутация `createCommitOnBranch` в GraphQL API создает единый атомарный коммит для массива файлов за один сетевой запрос.
3. **Бесплатный корпоративный аудит (Audit Log):**
   Каждое изменение в веб-интерфейсе фиксируется как коммит конкретного пользователя (`Evgeny Kosivtsov committed: chore(settings)...`). Всегда видна история, авторство и точный diff, а откат делается через `git revert`.

### 4.3. Сценарии использования Control Plane в браузере
* **Управление составом команды (`team.json`):** добавление разработчиков, смена ролей, указание алиасов без редактирования файлов в коде.
* **Настройки языка и правил (`locale.json`, `.cursor/rules`):** централизованное переключение языков общения Координатора и правил для агентов.
* **Управление сервисами стека (`project_profile.json`):** подключение новых репозиториев и микросервисов.
* **Снятие «зависших» задач (Force Idle):** если разработчик ушел в отпуск или забыл завершить сессию, тимлид нажимает кнопку на карточке Pulse, и Координатор коммитит перевод задачи в `idle`.

## 5. Фоновый процессинг: GitHub Actions как Serverless-обработчик

Для задач, требующих реакции на события команды, выделенный демон заменяется на **GitHub Actions**:
1. **Алерты о коллизиях в Slack/Telegram:**
   * При пуше в ветку состояния (`coordinator-state`) запускается Action `collision-check.yml`.
   * Action сопоставляет занятые сервисы из всех `.current_task_*` файлов.
   * При пересечении — отправляет мгновенный вебхук в корпоративный чат команды.
2. **Pull Request Gate:**
   * Action на этапе PR проверяет, была ли задача зарегистрирована в Координаторе и пройден ли `clean-main gate`.
   * Блокирует кнопку мерджа при наличии архитектурных нарушений.
3. **Регулярная агрегация аналитики токенов (FinOps):**
   * Ночной cron-Action собирает `events/*.jsonl`, формирует еженедельный отчет по эффективности затрат на AI и пушит готовый срез в ветку дашборда.

## 6. Сравнение архитектурных моделей

| Критерий | Классический облачный бэк (VPS / Docker / Coolify) | Бессерверный Git-as-a-Backend (GitHub Pages + API) |
|---|---|---|
| **Где крутится бэкенд** | На арендованном сервере компании | **Внутри штатной инфраструктуры GitHub** |
| **Стоимость хостинга** | $15–$50 / мес (сервер, SSL, домен) | **$0 (входит в базовую подписку GitHub)** |
| **Сложность обслуживания (Ops)** | Мониторинг демонов, обновления ОС, память | **Zero-Ops (нечему падать, нет серверов)** |
| **Уровень доверия безопасности** | Требуются проверки безопасности сервера | **Максимальный (данные не покидают GitHub)** |
| **Авторизация и роли** | Собственная БД пользователей / Auth0 | **Штатный GitHub RBAC и токены сотрудников** |
| **Интерфейс настроек** | Кастомная админка с записью в БД | **Веб-дашборд с прямыми Git-коммитами (sha-lock)** |

## 7. Итоговая рекомендация

Идеальная продуктовая связка для экосистемы Coordinator:
1. **Локальный агент:** хуки в IDE (`.cursor/`) перехватывают команды за `< 10 мс` локально.
2. **Шина состояния:** синхронизация снимков в изолированную ветку `coordinator-state` (ветка `main` остается чистой).
3. **Командный хаб:** бессерверный React SPA на **Private GitHub Pages**, читающий и коммитящий настройки напрямую через **GitHub API** под учетными записями инженеров.

## 8. Как сделано сейчас (вариант 1)

Принято: сиротская ветка `coordinator-state` в репозитории Common. GitHub Pages и Contents API из §3–5 сюда не входят.

* Агент по-прежнему читает `Common/data/progress/` на диске. Common остаётся на `main`.
* На `main` каталог `data/progress/` в `.gitignore` и снят с учёта. Settings и docs остаются в `main`.
* `sync_event.sh` / `log_event.sh` / `git_report` пишут файлы локально, затем `coordinator_state.sh` коммитит их в worktree `Common/.coordinator-state` и пушит `origin/coordinator-state`.
* Дашборд каждые 15 с тянет `main` (доки) и отдельно `coordinator-state` (снимки). `git pull` Common ставит `core.hooksPath=.githooks` и через `post-merge` / `post-rewrite` обновляет снимки, не переключая ветку.
