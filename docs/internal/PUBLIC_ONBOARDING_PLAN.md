Публичные MD (`docs/INSTALL.md`, `ONBOARDING.md`, `DEPENDENCIES.md`, корневой `README.md`) — **English**. Агент говорит с человеком на его языке. Этот план и концепция — internal, русский.

---

## 1. Цель

Отдать Координатора **чужой команде** (тимлид знакомого, пустой или уже живой проект) так, чтобы установка начиналась одной фразой в Cursor и заканчивалась живым дашбордом на этой машине.

Бета ставится **из открытого кода публичной репы**. Человек пишет в чат:

> установи координатора \<ссылка на MD установки в этой же репе\>

Cursor ведёт онбординг в чате, затем сам кладёт код, зависимости, правила и поднимает веб. В вебе открывается форма **создания координатора** (язык, проект, люди, роли доступа, папка реестра доков).

Первый полигон: **отдельный пустой проект**, не AlinaAssist. Разработка — в текущем `.coordinator`, с заложенной стратегией «эта репа станет публичной и её клонируют в чужой воркспейс».

---

## 2. Что меняется относительно старого онбординга

Документ `COORDINATOR_FOUNDER_ONBOARDING` описывал **два шаблона** (`.cursor` + `Common`), обязательную GitHub-орг и `gh repo create --template`. Для беты это слишком рано.

| Было (цель фаундера) | Бета (этот план) |
|---|---|
| Две публичные репы-шаблона | **Одна** публичная репа — этот `.coordinator` |
| Воркспейс всегда не-git, рядом `Common` и `.cursor` | Ставим **в уже открытый проект**; шина и доки живут **внутри репозитория проекта** |
| Org на GitHub обязателен до первого UI | Org **не нужен**, чтобы увидеть Координатора |
| Клон целого `.cursor` | **Инжект** пакета правил/хуков в `.cursor` хоста |
| Coolify / создание сервисов | Вне беты |

Старый документ остаётся целевым контрактом для «день, когда появился первый деплой и org». Бета его не реализует.

## 3. Зафиксированные решения

1. **Канал установки — Cursor-чат + живой MD**, не `curl \| bash` и не Homebrew (это post-beta, см. коммерческую концепцию).
2. **MD — исполнимый сценарий для агента**, не README «прочитайте сами». Человек почти ничего не копирует в терминал. Второй полной инструкции «для человека» нет: шапка в `INSTALL.md` отправляет человека в чат Cursor. Агент перед копированием правил **сверяется с уже существующим `.cursor` хоста** и кладёт пакет только в `rules/coordinator/`.
3. Каждый смысловой блок онбординга заканчивается вопросом **«готовы продолжить?»**. Агент не ставит код, пока человек не подтвердил.
4. После подтверждений агент делает **всю работу**: клон/копия репы, зависимости, инжект правил, сборка, запуск веба.
5. Первый экран веба — **мастер создания**, не пустой Pulse. Установщик на этой машине получает ACL **`admin`**.
6. **Роли Координатора ≠ роли в команде.** Команда: `founder` / `engineer` (и дальше). Доступ: кто может создавать людей и менять сетап.
7. Реестр доков — папка **во внутреннем git-репозитории проекта**, не в публичной репе Координатора и не «где-то на диске вне git».
8. **Монорепа — в скоупе беты.** Раскладку агент **предлагает в онбординге**, глядя на открытый проект; не молча и не впервые в веб-мастере. Мультирепа (как AlinaAssist) — в конфиг закладываем, детальную установку откладываем.
9. В публичную репу **не попадают** `Common/data` AlinaAssist, прод-секреты, клиентские промпты, Coolify UUID.
10. Пока репа не опубликована, тест идёт по **локальному пути** к тем же MD (тот же текст, другая ссылка).
11. **Публичные markdown — English.** Cursor переводит речь агента. Internal (`docs/internal/`) можно по-русски и установщику не отдаём.

## 4. Целевой UX

### 4.1. Вход

Человек открывает Cursor в папке проекта (пустой или с кодом) и вставляет промпт. Достаточно одной строки плюс URL:

```text
Install the Coordinator.
Playbook: https://github.com/AI-Team-Coordinator/.coordinator/blob/main/docs/INSTALL.md
```

Для теста до публикации:

```text
Install the Coordinator.
Playbook: /absolute/path/to/.coordinator/docs/INSTALL.md
```

Агент **сначала читает INSTALL.md** и следует ему. Не импровизирует установку «из памяти».

### 4.2. Онбординг в чате (до любых правок диска)

Порядок жёсткий. После каждого блока — стоп и вопрос «готовы продолжить?».

| # | Блок | Откуда текст | Зачем стоп |
|---|---|---|---|
| 1 | Идеология: фокус — команда; вход — один человек, который ставит себе | `docs/ONBOARDING.md` | Человек понимает, зачем это, до установки |
| 2 | Безопасность и доступы | тот же файл, секция Security | Согласие на хуки, git, локальные порты |
| 3 | Раскладка: агент **смотрит** открытый проект (только чтение) и предлагает вариант | `INSTALL.md` § раскладка | Не ставить «не в ту папку»; человек подтверждает схему |
| 4 | Сверка с уже существующим `.cursor` хоста | `ONBOARDING.md` + `INSTALL.md` | Не затереть чужие rules; не сложить два протокола |
| 5 | Шаги установки **для выбранной** раскладки (что агент сделает с диском) | `INSTALL.md` | Нет сюрприза «он уже клонирует / двигает папки» |
| 6 | Зависимости машины | `DEPENDENCIES.md` | Go / Node / git — до `brew install` |

Только после последнего «да» агент трогает файлы. Раскладку **не** откладываем на веб-мастер: к моменту клона она уже согласована. Сверку с `.cursor` тоже не откладываем: живой проект уже может иметь alwaysApply-правила; их нельзя затереть и нельзя молча сложить с чужим протоколом.

### 4.3. После установки

Открывается дашборд ([Coordinator](http://localhost:5175) в dev; в бете тот же контракт, что сейчас). Если профиль проекта ещё не создан — **мастер**, не обзор.

## 5. Раскладка на диске

### 5.1. Бета, монорепа (основной путь)

Человек сидит в git-корне проекта. Координатор кладётся **внутрь этой папки**:

```text
TheirApp/                     ← git, открыт в Cursor
  .git/
  src/ …
  .cursor/
    rules/coordinator/        ← инжект из пакета
    hooks/                    ← инжект + merge hooks.json
  .coordinator/               ← клон публичной репы (вложенный git)
  docs/                       ← реестр задач (путь выбирается в мастере)
  coordinator-data/           ← settings + progress (путь выбирается в мастере)
```

`TheirApp/.gitignore` дополняется: локальный `.env` координатора, `.current_author`, кэш, логи. Сам клон `.coordinator/` **не обязан** входить в git продукта: по умолчанию игнорируем его как tooling (обновление = `git pull` внутри `.coordinator`). Если тимлид хочет вендорить исходники — отдельный вопрос, не бета.

Шина и доки — **в git продукта**. Иначе команде нечего пушить друг другу.

### 5.2. Монорепа «на этаж выше» (воркспейс-родитель)

Если человек уже открыл вложенную папку (`TheirApp/app/`), корень Cursor не git, или рядом появятся ещё репы:

```text
Workspace/                    ← корень Cursor, сам не git
  .coordinator/
  .cursor/
  TheirApp/                   ← git продукта, здесь docs + data
```

Агент может **создать родителя и перенести/прописать** корень. Это спрашивается в онбординге, не делается молча и не прячется в мастер после установки.

### 5.3. Когда что предлагать (онбординг, только чтение)

До клона агент смотрит воркспейс: `pwd`, список файлов, `git rev-parse --show-toplevel`, есть ли `.git` у соседей. Один абзац «что вижу» + **одна рекомендация** + зачем + альтернатива. Человек соглашается или выбирает другое.

| Что видно | Предложить | Почему |
|---|---|---|
| Пустая / почти пустая папка, `git init` или ещё без git | **§5.1** внутрь | Пустой тест и один продукт; родитель ни к чему |
| Корень Cursor = корень одного git, в корне код (`package.json`, `src/`, …) | **§5.1** внутрь | Типичная монорепа; `.coordinator` рядом с кодом |
| Корень Cursor **не** git, один дочерний git | **§5.2** как есть | Воркспейс уже «этажом выше»; не двигать папки |
| Cursor открыт **внутри** git (toplevel выше воркспейса) | Сначала: открыть корень репо и **§5.1**. Иначе §5.2 | Проще не плодить родителя |
| Несколько соседних `.git` | §5.2 + шина в одном из репо; полная мультирепа — после беты | Не притворяться, что это один git |
| Уже есть `.coordinator/` | Не ставить заново | Это обновление / второй человек |

Создавать родителя и `mv` текущей папки — только если человек явно выбрал §5.2 **и** подтвердил список действий (какие папки появятся, что Cursor потом открыть на родителе).

### 5.4. Мультирепа (после беты)

Несколько соседних git, служебная шина в одном из них (у нас это `Common`). В конфиге уже будут `WORKSPACE_ROOT`, `BUS_DIR`, `DOCS_DIR`. Сценарий «найди все репы, спроси какая шина» — отдельный этап, не блокирует пустой монорепо-тест.

## 6. Состав публичной репы

Репа `AI-Team-Coordinator/.coordinator` — единственный дистрибутив беты.

```text
.coordinator/
  README.md                   ← English: one prompt + link
  docs/
    INSTALL.md                ← English, agent playbook
    ONBOARDING.md             ← English, chat copy
    DEPENDENCIES.md           ← English, machine checks
    internal/                 ← Russian, not for installers
      README.md
      PUBLIC_ONBOARDING_PLAN.md
      COMMERCIAL_CONCEPT.md
  pack/
    cursor-rules/             ← generic-правила без AlinaAssist
    cursor-hooks/             ← check-branch, research, merge-log
    hooks.json.fragment       ← что влить в hooks.json хоста
  backend/  frontend/  utils/      ← как сейчас
  .env.example
```

В пакет правил **не входят** `safety.mdc` прод-БД, клиентские промпты, Coolify, Inbox e2e. Только координация: protocol, voice, locale, parallel, research, show + тонкий `workspace.mdc` без привязки к `Core`.

Имена `Common` в правилах беты заменяются на **нейтральные**: «шина / bus», путь берётся из `.coordinator/.env` и из `locale.json` / профиля. Пока правила содержат хардкод `Common/`, чужой проект будет врать агенту — это обязательный кусок этапа обобщения.

## 7. Мастер создания в вебе

Показывается, если нет валидного `project_profile.json` **или** стоит флаг `setup.completed != true`.

| Поле | Поведение |
|---|---|
| Язык Координатора (`chat_language`) | `ru` / `en`; пишет `locale.json`. `docs_language` по умолчанию тот же |
| Название проекта | Автодетект: remote origin, `package.json` `name`, имя папки. Можно поправить |
| Раскладка | Только **подтверждение** выбора из онбординга (`in-repo` / `workspace-parent`). Не спрашивать впервые здесь |
| Папка реестра доков | Относительный путь внутри git продукта; агент/мастер проверяют, что путь в этом репо |
| Папка данных шины | По умолчанию рядом: `coordinator-data/` в том же репо. Settings + progress |
| Люди | Первый — текущий установщик: алиас, имя. Можно добавить остальных сразу |
| ACL Координатора | Установщик = `admin`. Остальные по умолчанию `member` |

После Save:

1. Пишутся `locale.json`, `team.json`, `project_profile.json`, `.current_author` (gitignore).
2. Пишется `.coordinator/.env` с `WORKSPACE_ROOT` / `DATA_DIR` / `DOCS_DIR` / `BUS_DIR` / `CURSOR_DIR`.
3. В git продукта: `.gitignore` на локальные файлы; первый коммит настроек **предлагается**, не делается без согласия (онбординг уже научил, что шина — git).
4. Дашборд переключается на обычный Pulse.

Создание GitHub-орг и сервисов из этого мастера **не делается**.

## 8. Роли: команда vs доступ

Сейчас в `team.json` одно поле `role` (`founder`, `engineer`) — это **должность на Pulse**, не права.

Вводим второе поле, например `access` (не переиспользовать `role`):

| `access` | Может |
|---|---|
| `admin` | Люди, язык, папки, профиль проекта, приглашение (когда появится) |
| `member` | Задачи, ресёрч, просмотр Pulse / журнала |

Бета: нет `viewer`, нет SSO. Проверка ACL — в API записи команды и профиля. Агент в чате смотрит `access` текущего `.current_author` и не предлагает «добавь сотрудника», если это `member`.

Роли команды (`founder` / `engineer` / …) остаются подписями. Их по-прежнему правит админ в том же экране «Команда».

## 9. Безопасность (что говорить в онбординге)

Координатор **local-first**: нет облака продукта, нет отправки кода на чужой сервер.

Нужны на машине:

- Чтение/запись папок проекта, `.cursor`, `.coordinator`
- Хуки Cursor (`preToolUse`, `sessionStart`, `afterAgentResponse`, `sessionEnd`) — иначе нет clean-main и голоса
- Локальные порты **4321** (API) и **5175** (Vite UI)
- `git` в репозитории продукта (коммиты шины — после согласия)
- Исходящая сеть: только git-хост публичной репы при клоне/обновлении; GitHub API — **не обязателен** в бете

Не просим: PAT в чат, доступ к прод-БД, Coolify-токены, права org-admin.

Хуки блокируют правки продукта на чужой ветке. Это и есть смысл Координатора, не «шпион».

## 10. Зависимости машины (бета)

Обязательные:

- **git**
- **Cursor** (хуки и правила)
- **Go 1.22+** (сейчас модуль `go 1.25`) — сборка API
- **Node 20+** и npm — `frontend/` (Vite)
- **Python 3** — хуки research / snapshot

Опционально: **GitHub CLI** — только если позже создаём репы или org. Для пустого теста не нужен.

Агент в блоке 5 проверяет версии, предлагает поставить через `brew` (macOS) и снова спрашивает «продолжить?». Сборку all-in-one бинарника без Go/npm **не делаем в бете**.

## 11. Что обобщить в текущем коде

Без этого INSTALL.md либо соврёт, либо поставит AlinaAssist-копию.

| Дыра | Зачем |
|---|---|
| Строки и пути `Common/data`, «сервисы AlinaAssist» в UI и ошибках | Чужой проект не Common |
| Правила `.cursor` заточены под AlinaAssist (`Core`, prod DB, промпты) | В пакет беты — только generic |
| Нет состояния «профиль не создан» | Мастер нечем показать |
| Нет `access` у члена команды | Некому быть админом установки |
| `CreateUnitForm` требует GitHub org | Не путь беты; мастер создания координатора — другой экран |
| Прогресс в `main` шины | Для чужой команды шум; связанная задача — orphan `coordinator-state`. В бете соло-теста допустим коммит в `main` продукта **или** gitignore progress до появления state-ветки |

Не обобщаем в бете: карту микросервисов Alina, Coolify, FinOps как продажу, мультирепо-клон всех сервисов.

## 12. Этапы работ

Разработка идёт **здесь**, в `.coordinator` (и пакет правил — копия в `pack/`, плюс позже инжект в `.cursor` хоста). Проверка — пустой проект.

### Этап 0 — план (этот документ)

**Готово**, когда план лежит в `.coordinator/docs/` и по нему можно писать живые MD.

### Этап 1 — живые MD (можно тестировать чат без готового мастера)

Файлы в публичной репе (**English**):

- `docs/INSTALL.md` — agent playbook, stop-questions, layout detect, host `.cursor` inspect (human header: paste the prompt, do not run the steps)
- `docs/ONBOARDING.md` — ideology + security + why two layouts + existing Cursor rules stay
- `docs/DEPENDENCIES.md` — machine checks
- `README.md` — one prompt for the human

Internal (русский): `docs/internal/PUBLIC_ONBOARDING_PLAN.md`, `COMMERCIAL_CONCEPT.md`.

`INSTALL.md` явно делит: «уже умеем» vs «ещё руками / ещё нет мастера». Первый прогон в пустом проекте проверяет **разговор, детект §5.1 и согласие**. Клон репы можно делать уже на этом этапе (код существует). Мастер веба может ещё отсутствовать — тогда агент пишет минимальный профиль файлами по чеклисту из MD.

**Приёмка:** в пустой папке фраза с путём к `INSTALL.md` → агент **описывает, что видит**, предлагает §5.1, не ставит ничего до всех «да» → после согласия появляется `.coordinator/`, зависимости, правила, поднятый UI.

### Этап 2 — пакет правил без AlinaAssist

**Сделано в репе:** `pack/cursor-rules/`, `pack/cursor-hooks/`, `pack/hooks.json.fragment`, `utils/install_cursor_pack.sh`.

- `pack/cursor-rules/` с нейтральной шиной (пути из `.env`: `DATA_DIR` / `DOCS_DIR` / `BUS_DIR`, не хардкод `Common`)
- merge `hooks.json`, не затирая чужие хуки
- инжект: `./utils/install_cursor_pack.sh`

**Приёмка:** в пустом проекте появляются только `rules/coordinator/*` и хуки координатора; нет `safety.mdc` прод-БД. В проекте, где `.cursor/rules` уже был, хостовые `.mdc` на месте; `hooks.json` дополнен, не заменён. Если в хосте уже есть конфликтующий alwaysApply-протокол — агент останавливается и спрашивает, не копирует пакет сверху. **Не** запускать инжект в AlinaAssist.

### Этап 3 — мастер создания + ACL

- API: создать профиль, locale, team с `access`
- UI: first-run вместо Pulse
- Админ может добавлять людей; member — нет

**Приёмка:** после установки открывается форма; язык ru; имя проекта сдетектилось; один admin; папка `docs/` создана в git проекта; Pulse виден только после Save.

### Этап 4 — выполнить выбранную раскладку

Детект и вопрос уже в этапе 1 (онбординг). Здесь — сделать на диске то, что человек подтвердил:

- §5.1: клон внутрь, `.env` на этот git
- §5.2: создать родителя / не двигать, если воркспейс уже родитель; `.env` с `WORKSPACE_ROOT` наверх
- Мастер только **показывает** выбранную схему

## 13. Как тестировать в пустом проекте (сразу после этапа 1)

1. Новая папка, `git init`, открыть её в Cursor (отдельное окно, не AlinaAssist).
2. В чат — промпт со **ссылкой на локальный** `INSTALL.md` этой репы.
3. Смотреть: стопы «продолжить?»; агент **сам описывает пустую папку и предлагает внутрь (§5.1)**; в блоке 4 говорит, что `.cursor` пустой или его нет, пакет ляжет в `rules/coordinator/`; нет скрытого клона до согласия.
4. После согласия: `.coordinator/` на месте, `npm`/`go` прошли, UI на [http://localhost:5175](http://localhost:5175).
5. Пока нет мастера — в `INSTALL.md` запасной путь: агент создаёт `locale.json` / `team.json` / папку доков по вопросам в чате.
6. Когда мастер готов — тот же прогон, но люди и язык задаются в вебе.

AlinaAssist при этих прогонах **не трогаем**. Регрессия: после правок `.coordinator` у себя по-прежнему `./utils/backend.sh restart`, Vite на 5175.

## 14. Порядок в этом репозитории

Пишем и запускаем здесь. Ветки фич в `.coordinator` по протоколу нет — `main`. Публичный origin тот же: `AI-Team-Coordinator/.coordinator`.

Не смешивать в один коммит: вычистку AlinaAssist-строк и ломающий инжект правил **этого** воркспейса. Сначала пакет `pack/` рядом, инжект в Alina `.cursor` — только когда generic-правила сознательно принимаем и здесь (отдельное решение: Alina остаётся на своих правилах, пакет — для чужих проектов).

Рекомендация: **AlinaAssist продолжает жить на своих `.cursor/rules`**. Публичный пакет — копия, которую установщик кладёт в *другой* проект. Расхождение потом сужаем, не наоборот в первый день.

## 15. Открытые вопросы (не блокируют этап 1)

1. Вложенный git `.coordinator/` vs submodule vs полная копия без `.git`. Для беты: **клон с `.git`**, в `.gitignore` продукта.
2. Имя папки данных: `coordinator-data/` vs `docs/.coordinator/`. В мастере по умолчанию `coordinator-data/` в корне git продукта, чтобы доки и статусы не смешивались в одном дереве markdown.
3. Лицензия файла LICENSE в день публикации — BSL 1.1 как в концепции, или временный более мягкий текст «beta, source available». Решить перед `git` public, не перед первым пустым тестом.
4. Нужен ли `gh` в онбординге беты — **нет**, пока не invitem второго человека через GitHub.
